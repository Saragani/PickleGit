01

Crashes & Races

Three bugs, one shape: code that assumed something was always present — a line on both sides of a diff, an exclusively-owned cancellation token — when it legitimately wasn't, because the UI lets more than one operation start before the first one finishes.

  • Side-by-side diff selection crash — GetSideBySideSelectableStart always reported a selectable start of 1 (skipping the leading diff-marker character), even for a padding row where one whole side is empty — a pure addition or deletion. Selecting text on that empty side then called String.IndexOf with a start index past the end of an empty string, throwing ArgumentOutOfRangeException. Made the function pane-aware so an empty-line pane reports a selectable start of 0.
  • Shared cancellation-token race → NullReferenceException — RunWorkAsync can run reentrantly while IsBusy is already true (Commit's CanExecute doesn't check it, so it can fire mid-Push). Both invocations wrote their own CancellationTokenSource into the same shared field before their first await — whichever call finished first disposed the CTS out from under the other, still-running call, which then crashed dereferencing it. Each call now captures its own CTS in a local variable and only clears the shared field in its finally if it still points at that same instance.
  • Operation-token race, the read side — fixing the disposal race above left the read side still exposed: a reentrant call could overwrite the shared field before the first operation's queued work had even started on the executor thread, letting OpToken — read from inside that work, e.g. a git.exe call via RunCliAsync — silently resolve to the wrong operation's token. Since GitExecutor runs exactly one queued item at a time on one dedicated thread, a [ThreadStatic] field set only for the duration each operation's work actually executes now scopes OpToken correctly, with no call-site changes needed.
⚠️

Found via PR review, not a bug report

The operation-token race was caught by pkl:review-pr while reviewing the credential-retry fix below — the CTS disposal fix alone looked complete, but review traced the read side too and found the second half of the same race.

02

Bitbucket OAuth, Fixed Twice Over

One user-reported symptom — "Bitbucket push/pull keeps asking for a password it won't accept" — turned out to have two independent causes stacked on top of each other. Fixing the first one just uncovered the second.

Bug 1 — the OAuth lookup was being skipped

  1. After a credential rejection, EnsureCredentialsAsync purges the stale credential and forces the next attempt to skip straight to a plain-text dialog — correct for the two PickleGit-owned cache shortcuts (its own store, the raw Windows Credential Manager fallback), which would just replay the same rejected value.
  2. It was also skipping the one OAuth-capable step — git credential fill, which drives Git Credential Manager's real browser OAuth flow for Bitbucket/GitHub — even though a fresh sign-in there could produce a genuinely new, valid token.
  3. Fixed to only skip the two cache shortcuts; the OAuth lookup always runs, now with up to 3 retries and a short backoff (a helper's cached value can take a moment to rotate right after being told it was rejected), and failed/empty attempts are logged via AppLog — never the credential itself.

Bug 2 — the token was correct, then broken on purpose

  1. With Bug 1 fixed, Git Credential Manager was confirmed (live, via curl against Bitbucket's own API) to return a valid, freshly-refreshed OAuth access token.
  2. PickleGit then took that valid token and forced it into a hand-built Authorization: Basic header regardless of where the credential came from. Bitbucket requires OAuth access tokens as Bearer, not Basic — confirmed with the same token via curl: Basic gets a 401, Bearer gets a 200.
  3. Added GitCli.HasConfiguredCredentialHelperAsync, which resolves the effective credential.helper for a remote URL via git config --get-urlmatch. Push, PushBranch, Fetch (single and all-remotes), and Pull now check this first — when a helper is configured, they skip PickleGit's own credential/header logic entirely and let git.exe negotiate Basic vs. Bearer itself, the same way a plain terminal git push already does correctly.
✅

Review caught four more before merge

A remote URL with embedded user:token@ userinfo could have reached GitCli's unconditional command logging (fixed with a new StripUserInfo helper); a native-path failure could purge an unrelated stale credential from a different operation; a stale _credentialsFromDialog flag could trigger a spurious resave on an all-native fetch-all; and four call sites had byte-identical SSH-vs-native branch bodies, merged into one condition each.

03

Merge Conflict Editor, Several Passes

The conflict editor got more attention than any other single view this round — five separate fixes, landing across four different sessions, each one surfaced by actually using the tool against a real conflict.

  • Merge commit message used to lose its file list — clicking Continue on a resolved merge shelled out to git merge --continue. Because GitCli always sets GIT_EDITOR=true, git treated that as an edited commit message and applied its default --cleanup=strip, silently stripping the # Conflicts: file list git itself had written. Continue now composes that message itself (source description + the originally-conflicted file list, read from MERGE_MSG before it's gone) and leaves it in the commit box for the normal Commit button to use — whose LibGit2Sharp call already detects MERGE_HEAD and adds the second parent correctly, with no cleanup pass to lose anything.
  • "Select All Mine/Theirs" silently reverted on an empty side — a conflict block whose Ours side has zero lines (a pure Theirs addition) made the include loop a no-op, and the derived Touched flag stayed false since no line ended up included — so the checkbox visibly reverted with no effect. An empty-but-explicit resolution is now a valid one: Touched is forced when the target side is empty and being checked.
  • Ligatures rendering only in the manual-edit pane — AvalonEdit ignores WPF's Typography.* attached properties entirely, so != rendered as a single glyph in the editable RESULT pane while every read-only pane (which sets those properties directly on a TextBlock) rendered it as two characters. Fixed via a DocumentColorizingTransformer that applies a hand-written TextRunTypographyProperties override per run.
  • Ctrl+G added to all four panes — go-to-line via the same shared DialogService.PromptForLineNumber prompt already used by the diff and blame views, wired into the three read-only panes' existing key handler and, separately, into the manual-edit AvalonEdit editor (which had no key handling wired at all before this).
  • Selection no longer clobbered by unrelated refreshes — two independent bugs, same symptom: an open conflict resolution or diff getting silently replaced by the Staged/Unstaged view whenever an unrelated repository refresh fired (an external tool touching the working directory, or just searching for a commit by hash). ShowWorkingDir was being forced to true on every refresh tick while a conflict was present, not just when one newly started; and a GraphNodes rebuild always reassigned SelectedNode wholesale even when the same commit was still selected, re-running LoadCommitDetail and clearing whatever file/diff was open. Both are now guarded — the first by tracking whether the previous refresh already had a conflict, the second via a shared ReselectSameCommit helper that repoints selection without re-triggering detail loading.

The last of the five is the one this changelog page's own session did — replacing AvalonEdit's own search UI in the manual-edit pane with the same themed find bar the other three panes already had:

04

Commit Graph, List & Sidebar

Four fixes to things the commit list and sidebar had been quietly getting wrong since much earlier — none of them crashed, which is exactly why they'd lasted this long.

  • "Uncommitted changes" drew a false edge into history — the synthesized pseudo-commit node declared the real top commit as its parent, so the graph drew a connecting line into history for changes that aren't actually committed yet. It no longer declares a parent at all — the lane frees immediately after the pseudo-commit row instead.
  • DATE/TIME column showed the wrong clock and the wrong sort — the column displayed each commit's own recorded UTC offset instead of the viewer's local time, and the list sorted/displayed by author date — preserved verbatim across a rebase/cherry-pick/amend, so a rebased commit's stale author date could land far from its real position in branch history even though the walk was topologically correct. Switched to committer date (matching SourceTree and Bitbucket's own list views) with proper local-time normalization; the commit detail panel's "Author: … / Date: …" pairing intentionally keeps author date, matching git show's own convention.
  • Truncated sidebar branch names had no way to read the rest — added a tooltip showing the full branch name whenever the sidebar row truncates it.
  • Stash rows: clutter and an unselectable click — libgit2's git_stash_save embeds a literal trailing blank line in the stash message whenever a custom message is passed, which rendered as extra blank lines under the title — now trimmed. Separately, the row's click handling used a routed-event MouseBinding that marked the click Handled before WPF's own selection logic ever saw it, so clicking a stash never actually selected it. It now goes through the same native selection-changed handler already used for Tag and Branch rows.
05

Diff, Blame & Dialogs

A grab-bag of navigation and rendering papercuts, plus one real off-screen-button bug in the app's own modal dialogs.

  • Go-to-line reached the diff and blame views — Ctrl+G, via the same shared prompt used everywhere else it now exists, added to the unified and side-by-side diff views and the blame view.
  • Hunk navigation scrolled to the bottom instead of the top — ListView.ScrollIntoView only scrolls the minimum distance needed, which lands a hunk header at whichever edge it was approached from — moving forward through hunks, that's the bottom. Replaced with a direct offset computed from the target row's index, reusing the diff view's own cached ScrollViewer reference, so the target hunk lands at the top of the viewport.
  • Long dialog content could push OK/Cancel off-screen — ConfirmDialog, TextPromptDialog, and ErrorDialog size to their content with no cap on the growing message region — a long enough message could push the button row past the visible desktop, or (for ErrorDialog's fixed 560px cap) past the window's own client area, leaving the buttons unreachable. Each dialog's message region is now wrapped in a ScrollViewer inside a flexible grid row, capped via a new DialogSizing.ForOwner that reads the actual monitor the dialog's owner is on (not just the primary monitor, which would keep the bug alive on any secondary display) with proper per-monitor DPI handling.
  • Icon glyphs rendering blank on Windows Server — every icon in the app declared a bare FontFamily="Segoe Fluent Icons", which only ships starting with Windows 11 — on Server 2019/2022 and other machines without it, the Private-Use-Area codepoints resolved against the theme's default font, which has no glyph there, rendering as blank space across the sidebar, commit detail panel, tab bar, and graph tag badge. Added a Segoe MDL2 Assets fallback (shipped since Windows 10 / Server 2016, same codepoints) across all 20 sites in three XAML files and one code-behind Typeface.
06

Code Quality Pass

A cumulative review across everything since v1.0.23 came back READY TO MERGE with zero CRITICAL/HIGH findings — but flagged a handful of small, cheap-to-fix issues worth closing out before the next tag.

  • Two silent catches, now logged — GetMergeConflictedFilePaths's bare catch { return result; } could have silently degraded the pre-filled merge commit message to just the source description with zero diagnostic trail; now logs via AppLog.Warn. DialogSizing.ForOwner's fallback got the same treatment, since a real (if rare) resolution failure there is worth knowing about.
  • Duplicated selection-sync logic, unified — ReselectSameCommit (added above, to stop refreshes from clobbering selection) duplicated the SelectedNode setter's SelectedNodes-sync sequence verbatim. Extracted into a single shared SyncSelectedNodesTo helper both call, so there's exactly one place that knows how to keep the two in sync.
  • Fetch-all-remotes resolved credential support one remote at a time — each remote's native-credential-helper check was awaited sequentially before the fetch itself even started; now resolved concurrently via Task.WhenAll, avoiding one avoidable subprocess-spawn wait per remote on multi-remote repos.

Net effect

No new surface area this round — every one of these is either a bug that used to produce wrong or missing behavior, or a consistency fix bringing one view in line with the other three that already worked correctly.
